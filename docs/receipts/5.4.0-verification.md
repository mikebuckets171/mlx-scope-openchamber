# 5.4.0 held-reading verification

Status: local checks passed; publication follows hosted CI. No real reply was sampled before publication: the owner
chose to skip the planned live check for this display-only change. The limits are at the end and are part of the result.

## Outcome

- Within a reply, the Session reading's last generation speed stays on screen, dimmed (`data-live="false"`), with its
  age (`≈ 43.2 tokens/s · 3 s ago`), through tool runs, the start of the next request, a prompt read without reported
  progress and the seconds before a new rate. A live reading replaces it; while a prompt is read, a live percentage or
  prompt-reading rate still shows.
- Before a reply's first speed, the reply's elapsed time fills those gaps, including a tool run.
- One source per reply: **This chat** (the `≈` estimate, or a runtime reading matched to the chat) gets the reply
  first. After it has shown, an **Engine** generation rate is not shown again until the next reply; a reply that
  started on Engine switches to This chat once.
- The held speed is frame memory only. It is dropped at the reply's end, on a stop, on a change of chat, chat model or
  connection, and on a paused or not-fresh frame. It is never stored, exported or shown as live. A prompt-reading rate
  is never held.
- Display only. The service bundle equals 5.3.0's except its embedded version string (`5.3.0` → `5.4.0`). The HTTP
  contract, polling, the service's reads, storage keys, permissions and the companion are unchanged.

## Completed checks

- Baseline before any change: `bun run check` passed with Bun 1.4.2 and reproduced the published 5.3.0 ZIP
  (`5c1d88fc…`) byte for byte.
- Final local run: type checking, privacy scan (680 files), 1,850 Bun tests (8 new), 81 companion tests, 15 ComfyUI
  helper tests, rebuilt bundles and package verification (36 assets, reproducible archive, bundle ceilings, CSP and leak
  checks, packaged-service smoke checks).
- Browser: all 630 Chromium/WebKit cases passed with two workers. Six are new: one Splash reply on the Session sidebar,
  the full page and the compact glance in each engine, driven live → no rate → held with age → prompt % → held → live
  → reply end. Run against the 5.3.0 bundle, all three Chromium cases fail where the number goes blank.
- Three existing specs (22 cases) asserted that the reading disappears during tool use and while the next request
  starts right after a live speed. They now assert the held reading (dimmed, aged, in the same row) and still assert no
  reading after a stop or a reply that ends without a rate.
- Presentation goldens: 21 pass unchanged at zero-pixel tolerance. None were regenerated: no golden state has an open
  reply.
- Overhead is unchanged by construction (display only; no polling or read change). The 5.2.0 overhead receipt stands;
  it was not re-measured.
- Splash 1.6.0 (status schema 8): every status field Scope's Splash adapters read is present in its server code. This
  is a static check, not a live reading.

## Limits

- No real reply was sampled or replayed before publication, so real-app timing (host turn windows, companion estimates)
  is confirmed by tests with fixtures only. If the improvement does not show in the app, the fallback is 5.3.0's
  behavior (the reading goes blank), not lost data.
- Rendering was checked in Chromium (the engine Electron uses) and WebKit in the fixture host, not in OpenChamber itself.
- The Nov 3 presence figure (63% of one-second samples) counted only the engine rate, on Splash 1.5.0; there is no
  comparable after figure.
